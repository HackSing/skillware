# askill-search 阶段 0 最小验证骨架方案

> 文档状态：待执行
> 方案日期：2026-08-16
> 依据：[PLUGIN_SPEC.md](PLUGIN_SPEC.md) 第 15 节阶段 0、第 20 节「实现前必须确认的七件事」、第 16.7 节验收层级
> 定位：这不是产品雏形，是**证伪装置**。目标是用最少的代码，尽快回答「这个项目的根本假设成不成立」。

## 0. 一句话目标

在**一个真实宿主**上，用一个能跑的最小 MCP Server，证明或证伪三件事：
两个只读工具能被稳定调用、原全量 Skills 注入能被真正关闭、关闭后模型仍会主动搜索并读取 Skill。
只要其中任何一件被证伪，就地停止，避免继续在 PLUGIN_SPEC 的 900 行细节上投入。

## 1. 原则

1. **证伪优先，不求完整**。先撞最致命的假设，不先建最漂亮的架构。
2. **能删就删**。凡是不影响回答上面三件事的东西，一律不做（见第 4 节）。
3. **真实任务为准**。可见字符只用来快速定位，最终结论以真实 API input tokens 和真实工具调用记录为准。
4. **单次不算数**。每个激活/召回判据至少重复 5 次，记录触发率，不用一次成功当结论。
5. **只读、不动用户文件**。骨架阶段绝不修改、移动、执行任何 Skill 文件；改宿主配置前必须先备份。

## 2. 阶段 0 要回答的关键问题（按致命度排序）

| # | 关键问题 | 为什么致命 | 对应实验 |
|---|---|---|---|
| Q1 | 两个只读 MCP 工具能否在目标宿主注册，并**无交互免审批**被调用？ | 调不动，一切归零。但 MCP 是成熟协议，风险最低、最先排除。 | 实验 A |
| Q2 | 目标宿主能否**真正关闭**原全量 Skills 注入？ | PLUGIN_SPEC 自称「项目最大的宿主集成风险」。关不掉 → 降本价值不存在。 | 实验 B |
| Q3 | 关闭注入后，模型面对专业任务是否仍会**主动调用** `skill_search` 并接着 `skill_read`？ | 关掉原目录后 Skill 靠模型主动发现。不触发 → Skill 实际不可用。文档单次测试提示需宿主级激活规则，需复验。 | 实验 C |
| Q4 | 上述达成后，真实首轮 input tokens 是否**明显下降**？ | 这是项目存在的唯一理由。前三问都过、这问不过，等于白做。 | 实验 D |

> Q2、Q3、Q4 相互耦合：必须先关掉注入（Q2），才能干净地测激活（Q3）和降本（Q4）。因此实验按 A → B → C → D 串行，任一环失败即触发停止条件。

## 3. 首个验证宿主（已定：Claude Code）

阶段 0 目的是「最快撞假设」，故选 **Claude Code** 为首个验证宿主：就在手边、原生支持 MCP、有明确的 skills 与配置机制、能直接观测首轮上下文，最快跑完 A/B/C/D。

> 偏离 PLUGIN_SPEC 原定的 Codex 是有意的：Codex 的 `skill_search` feature flag 按文档第 2 节记载不暴露所需工具，验证摩擦更大，不适合作为「最快证伪」的首选。Codex 留待阶段 0 在 Claude Code 上跑通、结论成立后，再按同一 Adapter 合同复验。

Core 与 MCP 部分保持**宿主无关**；只有实验 B/C 的具体操作（去哪关注入、去哪装激活规则）绑定 Claude Code。

## 4. 范围：做什么 / 明确不做什么

### 4.1 做（骨架必需）

- 一个最小 MCP Server（TypeScript + 官方 `@modelcontextprotocol/sdk`），暴露 `skill_search`、`skill_read` 两个工具。
- 两个工具声明只读安全元数据：`readOnlyHint=true`、`destructiveHint=false`、`openWorldHint=false`。
- 一个**内存级极简索引**：启动时一次性扫描单个写死目录下的 `SKILL.md`，解析 frontmatter 的 `name`/`description`（外加可选 `keywords`）。
- `skill_search`：名称精确匹配优先 + 关键词/描述子串匹配，返回最多 5 个摘要（不含正文）。够用即可，不追求排序算法。
- `skill_read`：读取入口 `SKILL.md` 及 Package 内单个相对资源，返回内容 + `content_hash`。
- **安全底线**（便宜且不可省）：路径规范化、拒绝 `..` 和绝对路径、读取前校验真实路径仍在授权根目录内。
- 一小批测试用 Skill 夹具（覆盖中/英、显式名、专业任务、无关任务），用于实验 C/D。

### 4.2 明确不做（留给阶段 1+，此刻做等于浪费）

- ❌ SQLite / WAL / `refresh.lock` / `migration.lock` / 迁移 / 崩溃恢复 / 多进程并发（内存索引足够回答 Q1~Q4）
- ❌ 增量索引 / 文件监听 / TTL `ensureFresh()`
- ❌ BM25/FTS/Embedding、`priority` 加权、项目上下文加权等完整排序
- ❌ `config.toml` 多库配置、CLI 全套命令（写死一个目录路径即可）
- ❌ `package_ref` 的完整短期授权与失效机制（骨架用最简形式或直接用 `skill_id`，安全校验保留）
- ❌ Host Adapter 的 `plan/apply/status/rollback` 完整实现（实验 B 用**手工、可回滚、先备份**的方式改配置，把「能不能关」这一事实先问出来）
- ❌ 性能 P95、1000 Skill 基准（骨架用几十个夹具）

## 5. 最小骨架结构

```text
askill-search/
├── docs/
│   └── PHASE0_POC_PLAN.md        # 本文件
├── poc/
│   ├── package.json
│   ├── tsconfig.json
│   ├── src/
│   │   ├── server.ts             # MCP Server 入口，注册两个工具 + 只读元数据
│   │   ├── index.ts              # 内存级极简索引：扫描 + frontmatter 解析
│   │   ├── search.ts             # skill_search：精确名 > 关键词/描述子串
│   │   ├── read.ts               # skill_read：入口 + 单资源读取 + 路径逃逸校验
│   │   └── config.ts             # 写死的技能库目录路径（唯一配置点）
│   └── fixtures/                 # 测试用 Skill 夹具
│       ├── react-review/SKILL.md
│       ├── wechat-writer/SKILL.md
│       └── ...（覆盖中英、显式名、专业任务、无关任务）
└── poc/EXPERIMENTS.md            # 实验记录：每次运行的条件、原始数据、触发率、结论
```

> 目标代码量：几百行量级。若某个文件开始膨胀成产品级实现，说明越界了，回看 4.2。

## 6. 验证实验设计

每个实验有：前置、步骤、**判据（可量化）**、失败处理。所有原始数据写入 `poc/EXPERIMENTS.md`。

### 实验 A — 工具可调用性（Q1）

- 前置：MCP Server 能启动，`tools/list` 返回两个工具。
- 步骤：在目标宿主注册该 MCP，发起一个显式调用（如 `$react-review`），观察是否成功完成 `skill_search` → `skill_read`，且**未弹交互审批**或审批被自动允许配置放行。
- 判据：两个工具均能被协议客户端调用；带只读元数据时不被宿主取消执行。
- 失败处理：若无只读元数据即被审批阻断，记录 `activation_blocked`；确认宿主是否提供对两个已知工具的自动允许配置。

### 实验 B — 关闭全量注入（Q2，最致命）

- 前置：先**备份**目标宿主的相关配置。
- 步骤：
  1. 侦测宿主是否存在**正式的全局关闭开关**（查配置/文档/实际行为，不假设它存在）。
  2. 若无，退到逐项禁用或「非自动发现目录」策略（把测试 Skill 放到宿主默认目录之外，只由本 MCP 索引）。
  3. 开新任务，测量首轮上下文中原 Skills 目录是否消失。
- 判据：首轮不再出现 Skill Library 的全量名称/描述/路径目录（以真实首轮内容为准，非仅可见字符）。
- 失败处理：若两条策略都无法消除全量注入 → **触发停止条件**，该宿主标记「局部不可用」，如实记录。

### 实验 C — 激活有效性（Q3）

- 前置：实验 B 已关闭注入。
- 步骤：准备三类任务各若干条，**每类重复 ≥5 次**：
  - 显式指定（`$name` / `/name`）
  - 隐式专业任务（如「审查这个 React 页面的性能问题」）
  - 简单任务（闲聊、翻译、直接事实问题）
  分别在「仅工具描述」与「加装 ≤500 字符宿主级激活规则」两种条件下运行。
- 判据（复用 PLUGIN_SPEC 16.4）：
  - 显式指定 `skill_search` 触发率 = 100%
  - 应搜索的专业任务触发率 ≥ 95%
  - 简单任务误触发率 ≤ 5%
  - 命中候选后 `skill_read` 完成率 = 100%
- 失败处理：若仅靠工具描述不触发（复现文档的单次结论），确认宿主是否提供稳定的全局激活规则渠道；若无 → 标记 `activation_unsupported`。

### 实验 D — Token 降本（Q4）

- 前置：A/B/C 通过。
- 步骤：同一宿主版本、模型、项目、任务集下做 A/B —— 「原全量注入」 vs 「关闭注入 + 两个工具 + 激活规则」，各测真实首轮 input tokens。
- 判据（复用 PLUGIN_SPEC 16.2）：
  - Skill 发现相关常驻上下文相对基线**减少 ≥ 80%**
  - 两个工具 Schema 合计 ≤ 1500 可见字符；激活规则 ≤ 500 可见字符
  - 真实首轮 input tokens 明显下降，方向与可见字符一致
- 失败处理：若净降本不显著（被工具 Schema 或激活规则抵消），记录净增量，重估项目价值。

## 7. 成功 / 停止条件

- **阶段 0 成功** = A、B、C、D 四个实验在**至少一个真实宿主形态**（如 Claude Code，或 Codex CLI 与 Desktop 分别）全部达标，并有可回滚的配置变更记录。达标后方可按 PLUGIN_SPEC 冻结 `ARCHITECTURE.md`、进入阶段 1。
- **就地停止**（任一即触发，如实记录，不粉饰）：
  - Q2 关不掉全量注入；
  - Q3 装了宿主级激活规则仍达不到触发率门槛；
  - Q4 降本不显著。

> 停止不等于项目失败——它可能只否定「当前宿主」或「当前策略」，通用 Core 仍可能成立。但**不能用低层证据冒充高层验收**（PLUGIN_SPEC 16.7）。
